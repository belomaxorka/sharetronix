# PHP 8.4 compatibility verification: 2026-10-18

Starting application revision: `820ef596b273f38092ad22762d1ac7b9246d7d3b`. Environment: Windows 11 x64; Apache 2.4.66 with rewrite/FastCGI; PHP 8.4.19 NTS; MySQL 5.7.44, empty SQL mode, `utf8`/`utf8_unicode_ci`. PHP 7.2.34 remains the behavior comparison runtime. This work does not migrate the database schema or declare other runtimes/databases supported.

The installer test can start a dedicated PHP 8.4 FastCGI process on loopback port 9074, with an isolated configuration, sessions, temporary directory, and PHP log. Its existing disposable Apache/site/database use port 8093. The ordinary local stack on 8092/9072 remains on PHP 7.2. `E_ALL` remains enabled; a completed PHP 8.4 run also requires no PHP warnings, notices, deprecations, or fatal/parse errors in its private log. Attempt metadata and responses remain under ignored `.local/installer-tests/` even when a check fails.

## Initial findings

The original PHP 8.4 installation reached the successful final redirect but failed the empty-body check. Its response contained the `pageDesigner::createTableDetailsBlock()` optional-before-required parameter deprecation. The same diagnostic occurred nine times in that fixture's PHP log. A full definition inventory with `error_reporting=-1` identified the same signature problem in `htmlBlock`, `layout`, and the two global form helpers in `func_html.php`; syntax exit codes alone had not detected these warnings.

Official references used for compatibility decisions: [PHP 8.4 deprecations](https://www.php.net/manual/en/migration84.deprecated.php), [PHP 8.2 dynamic properties](https://www.php.net/manual/en/migration82.deprecated.php), and [PHP 8.0 incompatible changes](https://www.php.net/manual/en/migration80.incompatible.php).

## Template and form signatures

`tests/php-signatures.php` failed on the original PHP 8.4 constructor declaration with diagnostics promoted to exceptions, while PHP 7.2 passed. Removed only the ineffective defaults before required parameters in four source files; argument order, names, references, and later defaults remain unchanged. Reviewed existing call sites, which supply the affected arguments.

The focused test then passed on PHP 7.2 and 8.4, exercising constructor argument/reference contracts, detail-table escaping/headings, empty data, and form action/row rendering. A new PHP 8.4 installation completed all 57 functional checks and its final response body was empty. The run correctly remained failing overall because the log contained 1,807 remaining diagnostics, primarily dynamic properties, plus date/cookie/activity-result/cron warnings. Those are handled separately.

## Existing runtime properties

Declared 37 existing properties across eleven classes, retaining their previous public visibility and untyped values. These are the specific fields observed during the full integration run; no blanket dynamic-property allowance or error-reporting reduction was added.

Before the patch, `tests/php-runtime-state.php` failed on `network::$cache` with deprecations promoted to exceptions. Afterward it passed on PHP 7.2 and 8.4: construction, valid/invalid CSRF tokens, serialization of user/token/shared-reference graphs, actual template/block loading and rendering, and comment author/date state were retained. All 57 PHP 8.4 integration checks again completed; dynamic-property diagnostics disappeared. The remaining log count was 29, from date formatting, a null logout cookie value, saved-result parsing in the activity handler, and the retired `E_STRICT` constant.

## Error-reporting constant and cron diagnostics

The worker evaluated `E_STRICT` before enabling displayed diagnostics, so its deprecation appeared only in the PHP log. Extended the worker regression to inspect a fresh private log as well as stdout and select PHP 7.2/8.4 explicitly. It then reproduced the failure despite an otherwise completed cycle and zero exit code.

Replaced `E_ALL | E_STRICT` with `E_ALL` in the four reporting settings. On the tested runtimes `E_ALL` already includes every applicable level; diagnostics are not masked. Complete due-job cycles and immediate repeats then passed on both PHP versions, including plugin execution, next schedules, zero running flags, and no logged/displayed diagnostics.

## Persistent-login cookie clearing

`tests/remember-cookie.php` reproduced the PHP 8.4 null-argument deprecation when rejecting an invalid persistent-login cookie. PHP 7.2 passed the same state checks. Both rejection and logout now pass an empty string to `setcookie()` instead of its formerly coerced null value; cookie names, paths, domains, expiration arguments, and session clearing are unchanged.

The strict regression passed on both runtimes after the patch, checking invalid-cookie rejection and clearing, logout identity reset, and removal of both login-session entries.

## Saved activity ID/type parsing

The posting handler split the saved `id_type` value, converted the entire variable into an integer, then tried to read its type as an array offset. The PHP 8.4 integration log recorded this warning on all three fixture publications.

`tests/activity-result.php` reproduced that warning by executing the real controller with synthetic persistence/rendering boundaries. Reading the type before integer conversion fixed the failure. The same strict test passed on PHP 7.2 and 8.4, checking numeric response IDs, public/private response types, and selection of `posts` versus `posts_pr`. No posting, visibility, or database-schema contract was changed.

## Profile month selector

After the preceding fixes, all functional checks completed but the PHP 8.4 log still contained 24 `strftime()` deprecations from the two profile-settings requests. Replaced that fixed English month-name conversion with `date('F', ...)`, retaining its timestamps/timezone and all twelve labels. The bundled language is English; alternative language packs/locales were not tested.

Extended the HTTP regression to verify every month option. A fresh PHP 8.4 installation then passed all 58 integration checks with zero PHP diagnostics. The same suite passed on PHP 7.2. This does not cover the other legacy date-formatting paths, which are checked separately when exercised.

## Language-package constructor

PHP 8 no longer treats a class-named method as its constructor. `tests/langpack-constructor.php` reproduced an uninitialized language package through the public `toArray()` result. Added `__construct()` delegating to the existing initializer, preserving its metadata/path building, missing-credentials guard, and explicit legacy method calls.

The strict test then passed on PHP 7.2 and 8.4, checking language key/name/version/folder, reinitialization, and the existing guard. It uses local metadata with network connection disabled; the retired marketplace is not contacted or claimed functional. PHP 7.2's old-constructor deprecation also disappeared.

## Post URL callback

The previously unexercised URL-rendering branch called removed `create_function()`. `tests/post-links.php` reproduced the PHP 8.4 fatal error, then passed on both runtimes after replacing only the callback factory with a closure. Exact output checks cover HTTP/FTP links, trailing punctuation, query-string escaping, and plain-text HTML escaping. The URL recognition expression and link builder remain unchanged.

Added an actual HTTP publication/direct-view check for a post containing a synthetic URL, without fetching that remote URL. This extends the integration suite to 59 checks.
